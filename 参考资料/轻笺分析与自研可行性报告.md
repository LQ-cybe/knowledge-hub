## 第一部分 轻笺调研

### 一、轻笺是什么

**一句话定位**：免费的开源"个人收集箱 + 整理台"——把散落在浏览器收藏夹、备忘录、微信/网盘里的书签、笔记、文件、待办放进一个地方，用**统一标签 + 全局搜索**串起来，再用**免费 AI** 补全、整理、问答。

| 维度 | 信息 |
|---|---|
| 官方站 | https://boluo66.top（免费在线使用，浏览器打开即用） |
| 开源仓库 | https://github.com/VeteranBoLuo/light-note（MIT，1723+ commits，活跃更新至 2026-09） |
| 技术栈 | 前端 Vue3+TS+Pinia+Vite；后端 Node.js+Express；MySQL5.7 + Redis + OBS 云存储；pnpm monorepo（apps/web、apps/server、apps/android、apps/host-agent、packages/shared） |
| 形态 | C/S Web 应用；有 Android 壳与 PWA；正常使用必须联网（数据在服务器） |
| 商业模式 | 永久免费；积分经济 + 爱发电赞助；AI 额度：游客 3 万/天、注册用户 25 万–200 万/天 |
| 空间 | 基础约 1G；积分扩容 +128MB=500分、+512MB=1600分、+2GB=5200分（各档限兑1次，合计上限 +2688MB）；爱发电可购空间（纯赞助） |

### 二、核心功能（六大模块）

| 模块 | 核心能力 |
|---|---|
| 📌 书签 | 粘贴链接自动抓标题/图标、网页快照防死链、死链体检、智能打标签、批量导入导出、地址自动纠错、置顶排序 |
| 📝 笔记 | 富文本/Markdown 双模式、内置+自定义模板、版本恢复、导出 PDF/MD、@提及书签/笔记/文件 + 反向引用、笔记助手（润色/改写/摘要/翻译） |
| ☁️ 云空间 | 文件上传（按类型/标签管理）、在线预览、分享下载、AI 分析（OCR）、空间扩容 |
| ✅ 待办 | 列表/议程/日历三视图、优先级、截止时间、单次/周期提醒（站内+邮件+日历）、重复任务、关联书签/笔记/文件 |
| 🏷️ 标签 | 跨资源统一标签、标签图谱/资源网络、相关标签自动推导（按共同标注）、批量编辑、标签图标 |
| 🤖 AI + 全局搜索 | 书签/笔记/文件/标签/待办跨模块统一检索；对话式 AI（可查数据、联网搜索、深度思考、参考来源可跳转） |

**补充能力**：工作台（概览+待处理+快速新建）、待整理（收集箱队列）、知识足迹热力图、浏览器扩展「随手收」（侧边栏，笔记可"带入当前网页文字"，单次上限约 5 万字）、书签栏快捷收藏工具（设置页激活，不装扩展也可用）、回收站、数据导出导入、跨设备同步、聊天室、积分/成长体系、快捷键。

**定位结论**：轻笺 = 个人「收集+整理」中枢。书签+云文件+待办+统一标签的**聚合能力是独一份**；但数据库/表格、团队协作、本地离线、插件生态是它的空白。

### 三、与主流知识库对比

| 产品 | 核心定位 | 独特强项 | 明显短板 |
|---|---|---|---|
| **轻笺** | 收集+整理中枢（书签/笔记/文件/待办聚合） | 网页剪藏与快照、统一标签图谱、全局搜索、免费 AI | 无数据库/表格、无多人协作、文件预览弱、空间 1G 起 |
| **Notion** | 全能工作台（页面+数据库） | 多维表格、页面嵌套、团队协作、公开 API | 免费版单文件≤5MB、国内访问不便、剪藏依赖插件 |
| **Obsidian** | 本地 Markdown 个人知识库 | 数据全在本地、双向链接图谱、社区插件生态极强 | 无内置剪藏/云盘/待办聚合，同步与发布要付费 |
| **印象笔记** | 传统笔记+剪藏 | Web Clipper 剪藏成熟、OCR、跨平台老牌 | 免费版设备/空间受限、偏封闭、广告打扰 |
| **语雀** | 结构化文档知识库 | 文档层级清晰、小记、团队协作、国内体验好 | 偏文档，无书签/云文件聚合；AI 与高级功能要会员 |

**选型一句话**：轻笺=攒资料（收藏+整理+AI）；Notion=搭系统（表格+协作）；Obsidian=深度写作+本地+插件自由；印象笔记/语雀=传统笔记与团队文档。

**关键认知**：轻笺与 Obsidian/Notion 不是同赛道替代品，而是互补关系。

### 四、扩展与二次开发可行性（三档结论）

| 路径 | 可行性 | 说明 |
|---|---|---|
| ① 官方插件体系 | ❌ 不存在 | 无第三方插件 API、无插件市场（帮助中心 151 篇无插件开发文档） |
| ② fork 开源魔改 | ⚠️ 可以但工程量大 | MIT、仓库活跃；官方定位 hosted service（托管服务），无一键自托管：需自搭 MySQL+Redis+对象存储+AI 服务 |
| ③ 外围自动化扩展 | ✅ 现在就能做 | 官方已提供浏览器扩展「随手收」+ 书签栏快捷收藏；可围绕它做自动化 |

## 第二部分 参考软件档案

### Notion
- **定位**：全能工作台（页面 + 数据库 + 协作）
- **强项**：多维表格/数据库视图（表格、看板、日历、画廊、列表）、页面无限嵌套、团队协作、公开 API + 大量集成
- **短板**：免费版单文件上传 ≤5MB；国内访问不便（需代理）；网页剪藏依赖插件
- **价格（2026 参考）**：免费版无限页面；Plus ≥$10/用户/月（年缴）/ €9.50；AI 试用付费
- **对自研的启发**：数据库（多维表格）是它和轻笺最本质的区别；API 生态成熟

### Obsidian
- **定位**：本地 Markdown 个人知识库
- **强项**：数据全在本地（纯文本文件）；双向链接（[[ ]]）与关系图谱；社区插件生态极强（数千插件）；免费
- **短板**：无内置网页剪藏/云盘/待办聚合；官方同步（Sync）与发布（Publish）要付费；移动端体验一般
- **对自研的启发**：双链图谱、插件体系的标杆；本地存储的信任感

### 印象笔记（Evernote）
- **定位**：传统笔记 + 网页剪藏
- **强项**：Web Clipper 剪藏最成熟、图片 OCR、跨平台老牌、稳定性
- **短板**：免费版设备数/空间受限、偏封闭、广告与推销打扰
- **对自研的启发**：剪藏体验是"收集"功能的参照

### 语雀（Yuque）
- **定位**：结构化文档知识库（蚂蚁集团）
- **强项**：文档层级清晰、小记、团队协作、国内网络体验好、Markdown 支持
- **短板**：偏文档场景，无书签/云文件聚合；AI 与高级功能要会员
- **对自研的启发**：文档树的组织方式、国内产品体验

### QuickLook（Windows 预览参考）
- **定位**：Windows 按空格快速预览文件（macOS Quick Look 移植）
- **性质**：C# 开源，**GPL-3.0**（商业授权需单独联系）；原理 = 调用 Windows 系统预览处理程序（IPreviewHandler）
- **结论**：**不集成其代码**（GPL 传染 + 独立浮动窗口无法嵌入）；若做原生客户端，可直接调用底层 IPreviewHandler（无 GPL 问题）
- **对自研的启发**：见"预览方案"章节

### wechatDownload（微信公众号批量下载工具，采集参考）
- **定位**：微信公众号文章批量下载（保存为 html/md/pdf/docx/csv 等）
- **性质**：**闭源软件 + 开源文档/Skill 接口**模式——GitHub 仓库（qiye45/wechatDownload）只有 README、示例、Issue 模板、给 AI 用的 SKILL/MCP 接口文档，**没有程序源码**；软件本体通过公众号「长风的储物柜」+ TG 群分发，另有远程 MCP 服务（changfengbox.top/api/mcp）
- **风险提示**：闭源 exe 运行需注意来源可信；批量抓取公众号文章涉及版权与平台条款（灰色地带）
- **对自研的启发**：①"闭源+文档开源"的社区运营模式；②网页采集的现实难度（反爬、动态渲染）；③MCP/Skill 给 AI Agent 调用的思路

## 第三部分 自研方案设计（已收敛）

### 五、范围决策

| 项目 | 决策 | 理由 |
|---|---|---|
| 架构 | **浏览器架构**（本地 Web 服务 / Tauri / Electron 桌面壳） | 界面美观、现代化、可拖拽；拖拽/图表/图谱库全现成；天然是本地软件 |
| AI 功能 | ❌ 首版忽略（可后期接入本地 Ollama 或云端 API） | 用户已本地部署过 Ollama + DeepSeek/Qwen |
| 云盘功能 | ❌ 首版忽略（本地文件管理为主，可选 WebDAV 同步） | |
| 网页采集 | ⏸️ 后期增加（浏览器扩展剪藏绕开反爬，参考「随手收」） | |
| 文件预览 | ✅ 首版做基础版 | PDF/图片/文本白送，Word 用 Mammoth.js |

### 六、核心模块定义

**① 工作台（概览看板 + 快捷入口）**——动作：**读全局**
- 统计卡（书签/笔记/文件数）、近期笔记、高频书签、内容趋势图、文件类型分布、待处理入口、快速新建
- 有图表，但核心是"从这里开始干活"，不是展示大屏

**② 资源中心（跨模块聚合检索）**——动作：**找东西**
- 全局搜索框 + 分类结果流（书签/笔记/文件分栏）+ 标签过滤 + 关键词+标签联合检索 + 点击跳转详情
- 本质是"搜索引擎落地页"，不是仪表盘

**③ 整理中心 / 待整理（收件箱队列 + 批量处理）**——动作：**做归类**
- 未整理资源列表 + 批量打标签/移动/归档 + 拖拽归类 + 与待办联动
- 像邮箱 Inbox，攒着待归类的东西逐条/批量处理

**④ 标签图谱（标签与资源网络）**
- 标签、书签、笔记、文件之间的关系；相关标签按"共同标注"自动推导
- 交互：查看 + 轻交互（点击看关联、拖拽整理布局）；增删改走右键菜单或回列表操作

**三者闭环**：收集进来 → 整理中心(做归类) → 沉淀进标签体系 → 工作台(看全局) ← 资源中心(找内容)

### 七、视图范式辨析（列表 / 议程 / 日历）

**关键认知：议程不是"日视图放大版"，两者是并列范式——"维度"不同**

| 视图 | 范式 | 本质 |
|---|---|---|
| 列表 | 平铺列表 | 看"我有哪些事" |
| **议程** | **一维线性流**：按时间分组（今天→明天→本周→更晚）往下延伸 | **顺序本身就是时间**，没有格子坐标系 |
| **日历** | **二维网格**：行×列交叉定位 | 任务放进格子里靠行列坐标；日/周/月只是粒度缩放（原理相同） |

- 议程实现 = 按截止日期 `GROUP BY` 分组渲染（★ 简单）
- 日历实现 = 网格布局 + 跨天任务 + 重叠布局（★★★，有布局算法，参考多维表甘特图/日历的经验）
- 两者是独立功能，分开排期

### 八、数据模型（统一资源模型）

**核心思想：一切皆资源、皆有唯一 ID、关联全靠外键——全部内容用数据库方式存储**

```
resources（统一资源表）          ← 书签/笔记/文件/待办都是它的一行
├─ id          TEXT PK（UUID）
├─ type        bookmark | note | file | todo
├─ title
├─ content / url / path          ← 按 type 使用对应字段
├─ created_at / updated_at

tags（标签表）
├─ id  PK
├─ name（唯一）

resource_tags（资源↔标签 多对多）
├─ resource_id → resources.id
├─ tag_id      → tags.id
└─ 统一标签、图谱、整理中心的底层

note_links（笔记↔笔记 双链）
├─ source_id → resources.id
├─ target_id → resources.id
└─ 链接存 ID 不存标题（见第十章）
```

**两条"快"要分清楚**：
- `id` 主键索引 → 按 ID 精确定位（打开/跳转）毫秒级
- **FTS5 全文索引** → 内容关键词搜索（资源中心）——中文分词是唯一需要专门处理的地方

### 九、检索方案
- SQLite **FTS5** 虚拟表做全文索引（一天跑通）
- **中文分词是唯一真坑**：默认分词器不切中文；用 `simple`/`trigram` tokenizer 或 jieba 预分词写入索引列（成熟方案）
- 跨类型聚合：多查询 union 后归一化展示

### 十、图谱与双链

**三种方案的难度梯度**：

| 方案 | 形态 | 成本 |
|---|---|---|
| 标签图谱（已定） | 标签-资源网络（渲染：ECharts graph / AntV G6） | ★★（2-3 天） |
| @ 提及 + 反向引用 | 轻笺式轻量双链（笔记里 @ 书签/笔记/文件） | ★★☆（+1-2 天） |
| Obsidian 式 [[ ]] 双链 | 完整双链（节点=笔记，边=引用） | ★★★（+3-5 天） |

**双链增量分析**（标签图谱 → [[ ]] 双链）：渲染层/交互层**零增量**（图库不变，节点换成笔记、边换成引用）；增量全在数据层（note_links 表 + 解析 [[ ]] 语法 +1-2 天）与计算层（目标解析、重名歧义、完整性维护 +2-3 天）。

**链接完整性：存 ID 而不是存标题**（Access 外键语义的复刻）

| 场景 | 标题链接 [[旧名]] | ID 链接 [[显示名\|ID]] ✅ |
|---|---|---|
| 改名 | 全文替换文本 | 只改显示名，链接不动 |
| 重名 | 歧义 | 无影响 |
| 删除 | 查引用后拒绝 | 查引用后拒绝（一条 COUNT） |

- Access 免疫断链的真正原因：**外键指向主键 ID，不存名字**
- 轻笺 @ 提及、Notion 链接底层都存 ID——不是巧合
- 图谱技术选型：起步用 ECharts graph（与工作台图表同一套库）；二期交互增强换 AntV G6；几千节点时按标签分组布局/懒加载展开

### 十一、文件预览方案（QuickLook 集成分析）

**结论：不集成 QuickLook 本体**（GPL-3.0 传染 + 独立浮动窗口无法嵌入）；PDF/图片在浏览器架构下是"白送"的（比轻笺在线预览体验更好，还能选中复制）。

| 文件类型 | 方案 | 成本 |
|---|---|---|
| PDF | 浏览器原生 `<iframe>` / pdf.js | 白送 |
| 图片/文本/MD | 浏览器原生 | 白送 |
| Word docx | **Mammoth.js** 纯前端 docx→HTML（阅读级，复杂排版丢格式） | 低，半天 |
| Excel/PPT | 首版砍掉，二期再说 | 后期 |
| QuickLook | 不集成；最多"外部预览"按钮唤起用户已装的 QuickLook | 可选 |

### 十二、工作量与难度评估

前提：个人开发者 + Web 技术栈 + 本地单机，估算值（示意）。

| 模块 | 难度 | 核心技术点 | 预估 |
|---|---|---|---|
| 工作台 | ★☆☆ | COUNT 统计 + ECharts 现成组件 + 最近项列表 | ≈ 1-2 天 |
| 资源中心 | ★★☆ | SQLite FTS5 + 中文分词 + 分栏聚合 | ≈ 3-5 天 |
| 整理中心 | ★★ | 未整理筛选 + 批量操作（事务）+ 拖拽归类 | ≈ 2-3 天 |
| 标签图谱 | ★★ | 相关标签 COUNT+JOIN + ECharts graph / G6 | ≈ 2-3 天 |
| @提及/双链（可选） | ★★~★★★ | note_links + 解析；ID 链接可大幅降难度 | +1-3 天 |
| 文件预览 | ★ | PDF/图片原生；Word Mammoth | ≈ 1-2 天 |
| **合计（不含双链）** | | | **≈ 2-3 周** |

**⚠️ 隐藏难度变量：「文件管理」的范围**：只做结构化数据（书签/笔记/待办）→ 普通 CRUD；混入二进制文件 + 在线预览 → 难度跳级（Word/PDF 渲染管线是深坑，轻笺自己都做不好，首版只做"文件名/元数据级"管理）。

**对比参考**：轻笺 1723 次提交的工程量，绝大部分花在采集、AI、同步、移动端——正是本方案砍掉的部分。

### 十三、结论与下一步

**结论**：
1. 轻笺核心价值是"书签+文件+待办+统一标签+AI"的聚合，技术单点都不复杂；
2. "能开发完成"成立，浏览器架构下比轻笺在线架构更简单（绕开服务端转换/同步深坑）；
3. 按收敛范围，**2-3 周可出可自用的单机 MVP**。

**待定决策（开工前确认）**：
1. 首版资源类型是否包含二进制文件？（决定"文件管理"难度）
2. 前端框架：Vue3 / React / 纯 HTML？
3. 载体：纯本地 Web 服务（localhost）还是 Tauri/Electron 桌面壳？
4. 图谱是否需要"编辑"（图上增删关系），还是仅查看+跳转？
5. 双链做哪种：标签图谱 / @提及反向引用 / [[ ]] 双链？

**建议开发顺序**：数据模型（四张表+索引）→ 书签+标签+搜索（资源中心）→ 工作台 → 整理中心 → 图谱 → 预览 → 双链（可选）
