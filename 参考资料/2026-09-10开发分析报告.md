### 4. 排障攻坚一：鱼骨图斜线"断开"（Task 33）

**现象**：二级节点下方的斜线没连到节点（用户配图），肉眼可见一段缝。

**根因**：斜线端点画在**节点矩形包围盒的角点** `(item.left, item.top + item.height)`，但节点是**圆角矩形**（本项目所有主题 `borderRadius = 10`），包围盒角点在圆角轮廓**外侧**，沿对角线偏离轮廓 `r × (√2 − 1) ≈ 4.14` 单位——**不是"差一点"，是几何必然**。

**修复**（`web/smm-patches/Fishbone.js` 新增 `reachNodeOutline()`）：
- 从包围盒角点沿连线方向以 **0.2 为单位步进**；
- 用「点到内部收缩矩形的距离 ≤ r」判定是否进入节点内部；
- 取首个进入点后再**向内压 2**（节点容器绘制在连线之上，压进去的一小段被填充色遮住，不留发丝缝）。

**验证**：8 条斜线端点 SDF = −0.8 ~ −1.3（负值 = 已在节点内部），控制台 0 报错。

**迭代过程**：用户先反馈"包围盒能不能去掉，直接按节点自身形状来说选择"——彼时我误判为斜线连接目标问题，实际是两件事；用户第二次澄清后拆分为「斜线贴合轮廓」+「选中高亮框贴合形状」两个独立修复。

### 5. 排障攻坚二：节点选中/悬停"包围盒"改造

**需求**：选中节点时那个比节点大一圈的外框（`.smm-hover-node`）去掉，高亮按节点自身形状来。

**实现**（是 `nodeLayout.js addHoverNode`）：尺寸 = 节点 + `hoverRectPadding × 2`，位置 `(-padding, -padding)`，圆角取 `style.hoverNode` 的 `hoverRectRadius`。

**改法（只动 `web/src/MindmapView.vue`，无需改 node_modules）**：
1. `new MindMap({ ..., hoverRectPadding: 0 })` → 高亮框尺寸 = 节点尺寸；
2. `themeCfgFor` 里把 `hoverRectRadius` **逐层**写进 `root/second/node/generalization`。

**重要坑**：SMM 构建 themeConfig 用 `deepmerge(内置主题, opt.themeConfig)`（`utils` 的 `mergeTheme`），内置主题**每一层**都带 `hoverRectRadius: 5` → **只写在最外层会被层级值盖掉**（第一次实测 rx 仍为 5，就是这个原因）。

**验证**：选中后 `.smm-hover-node` `x=0,y=0,w=64,h=35,`**`rx=10`**，与 `.smm-node-shape` 只差 0.9px（= 描边半宽）。

### 6. 排障攻坚三：**"重叠又回来了"的定性——旧预打包依赖**（今日最长单点）

**现象**：用户截图显示「六顶思考帽」第一个分支的长子节点（530×74）把右侧三个分支的子节点全罩住，与上一轮修好后实测结果不符。

**定性方法（可复用：从用户截图反推代码版本）**：
1. 对截图做**填充色连通域**分析（`abs(rgb-target).sum() < 14`，比亮度阈值稳），定出每个节点框；用已知节点「直觉判断」87×31 layout → 截图 173×63 标定出**缩放系数 = 2.0**；
2. 量第一层节点 `left`：模板说明 190.5 / 白色思考帽 295.5 / 黄色思考帽 416.5 / 蓝色思考帽 537 → 相邻间距 **105 / 121 / 120.5 = 节点自身宽度(94/110) + marginX(10.5)**；
3. 对照当前补丁版实测：间距 **588 = 子树宽度(578.5) + marginX(10)**；
4. **结论**：用户浏览器跑的是**未打补丁的官方公式**（`computedLeftTopValue` 里 `topTotalLeft += item.width + marginX`）→ 页面持有**旧的预打包依赖**，不是数据问题（DB 里 `expand` 全为 1，代码逻辑走不到折叠分支）。

**根因（两条环境因素叠加）**：
1. **stray vite 实例**：`start-hidden.vbs` 原来**无条件**启动后端 + 前端，端口被占时 Vite 静默递增到 5179/5180/…；多个实例共享同一个 `web/node_modules/.vite/deps` → 互相重写预打包缓存 → "补丁失效"；
2. **页面长期不重载**：老标签页继续跑旧 chunk，直到手动硬刷新。

**处置**：
1. `start-hidden.vbs` 改**幂等**：先 `netstat … | findstr LISTENING` 探测 5177/5178，只启动未监听的（保留原 10s 重试逻辑）；保持**纯 ASCII**（非 ASCII 字节数 = 0）+ CRLF；
2. `web/vite.config.ts` 加 `server.strictPort: true`：端口占用直接失败，不再自动递增产生游离实例；
3. 清掉 5179 游离实例 + `rm -rf node_modules/.vite` + 重启单一 vite 实例。

**❌ 试过但不可行（务必别再试）**：
- `optimizeDeps.force: true`：想"每次启动强制重建依赖"根治缓存，结果 vite 启动直接失败——WorkBuddy 注入的 `node-safe-delete-shim.cjs` 拦截了 vite 的 `fs.rm` 批量删除（`[SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":73,"threshold":50}`）。
- `optimizeDeps.exclude: ['simple-mind-map']`：SMM 有 `eventemitter3` 等 **CJS 依赖**，排除预打包后浏览器报 `does not provide an export named 'default'`（已实测复现，页面白屏）。
- **结论**：`simple-mind-map` 必须走预打包；改补丁后固定流程仍是「cp 到 node_modules → `rm -rf web/node_modules/.vite` → 重启 vite → 硬刷新」。

**验证**（Edge CDP 无头，`kh-final.mjs`）：六顶思考帽 21 节点、`.smm-node-container` = 1、**两两重叠 0**、分支间距 588、控制台 errors = 0；放射布局测试 30 节点、重叠 0。

### 7. 第 26 轮（收尾）：思维导图节点间距校准

**用户诉求**：
1. 子节点之间纵向间距被"完全消掉"（两节点直接挨着）→ 要留 10px 空白；其它视图同理（**注意组织图是横向**）；
2. 左右视图（向右/向左）+ 思维导图这 3 个视图里，**两个分支节点之间的纵向距离太大**，减掉一半。

**根因**：SMM 实际间距 = `marginY + hoverRectPadding × 2`，而**内置默认 `node.marginY = 0`**——子节点之间本来贴死，一直靠 `hoverRectPadding: 2` 提供的 4px 撑着。**第 26 轮前半为去掉"选中包围盒"把它改成 0，这点空白也一起消失** → 节点贴死。**不是布局塌了，是上一步改动带出来的副作用。**

**改动（只动 `web/src/MindmapView.vue` 的 `themeCfgFor`）**：
```ts
cfg.node = { ...(cfg.node || {}), marginY: 10 };                   // 所有布局 —— 子节点留 10px
if (['right', 'left', 'mind'].includes(layoutKey.value)) {
  cfg.second = { ...(cfg.second || {}), marginY: 10 };             // 内置 40 → 10，分支间距减半
}
```
- 组织图是横向布点，它的「兄弟间距」恰好读 `marginY`（`OrganizationStructure.js:89`）→ 同一数值正好给它 10px **横向**间隙；
- 鱼骨图 / 时间轴的 `second.marginY` 含义不同（按夹角、按轴线排布），保持默认没动。

**A/B 实测（参数校准依据）**：

| `second.marginY` | 说明→红 | 红→白 | 白→绿 | 绿→黄 | 黄→黑 | 黑→蓝 | 总高 |
|---|---|---|---|---|---|---|---|
| 40（你的截图状态 / 基线） | 60.5 | 59.5 | 78 | 78 | 78 | 98.5 | 750 |
| 20 | 40.5 | 39.5 | 58 | 58 | 58 | 78.5 | 630 |
| **10（采用）** | **30.5** | **29.5** | 48 | 48 | 48 | 68.5 | 570 |

（单位 = 布局像素；数据取自「六顶思考帽」向右布局第 2 层相邻间隙）

- 我按用户截图的真实数据校准过：分支框高 37px、间隙 68/62/78/78/78/95（**图内像素**，scale ≈ 1.07）→ 折算 **58~89 布局像素**，目标"一半"≈ 29~45。**前两条正好 −50%**；带 3 个子节点的分支只能 −30%，因为「子树撑开量」是防重叠的**刚性下限**（`updateBrothers` 会把子树高度溢出的一半推给邻居，压不下去）。
- **判断"参数是否生效"不能只看单个间隙**——子树撑开量会叠加进来。做法：**改前/改后各跑一次 A/B**，看差值是否等于参数差。

**回归（Edge CDP 无头，5 导图 × 8 布局）**：
- 六顶思考帽（6 种布局）：21 节点、画布容器 1、**两两重叠 0**、纵向最小间隙 **10**；

### 耗时结论

- **"重叠复发"的定性是今日单点之最**：症状看起来是"代码回退"，实际是**环境缓存**问题。最有价值的动作不是改代码，而是**用截图反推出页面跑的是哪一版公式**（间距 = 节点自身宽度 + 10.5 → 官方版）——这一步把排查范围从"布局算法"直接收敛到"依赖缓存"。
- **鱼骨图斜线的根因有隐蔽性**："差一点点"的表象下其实是**几何必然**（圆角矩形与包围盒角点沿对角线差 `r(√2−1)`）。放大截图 + SDF 量化才能把"看起来没连上"变成"端点 SDF = +4.14"的确定数值。
- **SMM 的 themeConfig 是 deepmerge 语义**：层级配置（`root/second/node/generalization`）会覆盖最外层同名键，写主题参数必须**逐层写**，否则静默失效（第一次 `hoverRectRadius` 就是这么没生效的）。
- **两次"自引入副作用"占了不少时间**：`hoverRectPadding: 0` 去掉包围盒 → 连带把子节点间 4px 空白也去掉了；`optimizeDeps.force` 想根治缓存 → 反而起不来。教训是**改一个参数前先确认它被哪些逻辑共用**。

## 四、经验与结论

1. **"看起来像回归"的问题要先分辨"代码版本"还是"运行环境"**：截图连通域反推参数（间距 = 节点自身宽度 + marginX）是今天最有效的一招。批量验证手段：`grep -c <补丁符号> node_modules/.vite/deps/chunk-*.js`（**不要写死 chunk 文件名**，hash 会变，要 `for f in chunk-*.js` 扫）。
2. **多实例共享预打包缓存是"补丁失效"的元凶**：`start-hidden.vbs` 无条件启动 → Vite 端口递增 → 5179/5180 与 5178 共享 `.vite/deps` 互相覆盖。已用「幂等启动 + `strictPort: true`」双向堵住。
3. **SMM 主题参数必须逐层覆盖**：`deepmerge(内置主题, opt.themeConfig)`，内置主题每层都带默认值，只写最外层会被层级值盖掉。同理 `hoverRectPadding` 会影响**实际间距**（`marginY + hoverRectPadding×2`），改它要连带补 `marginY`。
4. **圆角矩形节点的连线端点不能落在包围盒角点**：沿对角线偏离 `r(√2−1)`，视觉上必然是"断开"。正确做法是沿方向步进 + SDF 判定推进到真实轮廓。
5. **精确回滚优于整体 revert**：先 `git ls-tree <target> -- <dir>` 确认目标提交里**到底有哪些补丁文件**（本次发现第 4 轮并无 `fishboneUtils.js`），再按文件粒度回滚，既回到验收状态又不丢后续功能。
6. **量间距必须先除视图缩放**：543 节点的导图自适应后 scale ≈ 0.05，直接拿屏幕像素比会得到 0.5px 的假结果、误判成"参数没生效"。`scale = 屏幕框宽 / getBBox().width`，逐节点求中位数。
7. **从用户截图反推参数要按"行方向"做连通域**：按列扫描会被文字切断成 10px 小段；按行统计同色像素数才能拿到完整节点框，再用已知节点高标定 scale。
8. **改同一文件的多处必须串行 Edit**：两个 Edit 并行发，其中一个会被静默丢弃但返回 "Successfully edited"（本次表现为 `getTags is not defined` 运行时错误）。全局换公共组件时必须同步检查 `<script setup>` 的 import 列表。
9. **Vue mounted 报错定位要看 consoleAPICalled**：`Runtime.exceptionThrown` 的 `exception.text` 只给 "Uncaught (in promise)"，真正的 `ReferenceError` 藏在 `Runtime.consoleAPICalled` 的 warn 里。
