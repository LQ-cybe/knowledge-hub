# 设计原理

`icon-design` 是一个围绕本地图标目录构建的图标检索 skill。它不是在线图标网站镜像，也不是前端组件库封装，而是一个更适合 AI 协作的本地检索层。

## 为什么必须通过脚本而不能直接读数据文件

`./data/` 下的 JSON 索引和 catalog 是脚本私有的内部格式，仅供脚本运行时解析。直接读取这些文件会导致：

1. **多图库同名冲突**：多个图库存在大量同名图标（如多个库都有 "search"），裸文件名不唯一，直接读必然拿错
2. **uniqueKey 编码规则由脚本维护**：手动解析会出错，且脚本内部可能随时调整编码规则
3. **颜色和尺寸依赖脚本逻辑**：PNG/ICO 导出需要 Edge 无头截图，颜色替换需要脚本内的 SVG 处理流程

**因此：AI 获取图标数据的唯一合法途径是通过 `./scripts/` 下的三段脚本调用。**

## 为什么要在 HTML 里展示组合名

多个图标库合并后，单独文件名不再唯一（如 `iconpark` 和 `heroicons` 都有叫 "search" 的图标）。

所以 HTML 结果页里需要明确展示一个稳定的唯一键（uniqueKey），方便用户直接复制给 AI，避免"从上往下数第 3 个"这种不稳定的引用方式。

## 为什么最终按 uniqueKey 取 SVG

HTML 页面序号会随着搜索结果变化而改变，裸文件名在多图库场景下也会重名。因此统一使用 `uniqueKey` 作为图标的唯一标识。

格式示例：

- `iconpark:02102:Base:search`
- `iconpark:00972:Edit:find`
- `heroicons:20:solid:magnifying-glass`

## 不做的事

- 不负责复杂的图标二次设计（重画路径、拼接多个图标）
- 不把页面序号当永久标识
- 不依赖上一轮会话记忆页码
- 不要求用户理解图标仓库结构
